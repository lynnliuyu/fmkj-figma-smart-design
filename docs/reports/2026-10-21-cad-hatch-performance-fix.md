# 真实 DWG 导出：HATCH 变换缺陷与修正版实测

日期：2026-10-21（Asia/Shanghai）。客户原图与输出只存 `.local/` 忽略目录；原 DWG 仅读，未写项目数据库或客户固定交付。

## 新结论

首轮“CADCraft + Python 路径性能不达标”的观察属实，但不能把原因全部归于这类路线本身。继续诊断发现，仓库原锁定的 **ezdxf 1.4.4** 在展开 INSERT 时会重复应用 HATCH 的比例 / 角度，并遗漏图案原点平移。改用正式版 **1.4.5** 后，同一份 DWG 的 `平面图` 布局 **13 张已通过真实 HTTP 接口完整生成，上传到结束共 99.401 秒**，渲染进程采样峰值物理内存约 **406.8 MiB**。

这证明目前已可生成该布局的整套审阅资料，尚不等于所有内容与源 CAD 正式打印完全一致。另有单独的缓存 DXF 渲染试验为 55.44 秒，不包含上传、DWG 解码、图框识别和 PDF 合并，不能混作网页总耗时。

## 根因与一手证据

最小复现使用真实 `INSERT.virtual_entities()` 调用：块内 AR-SAND 的 `pattern_scale=0.005`，只把块从原点平移到 `(-16000,4200)`。1.4.4 将实际线间距从约 `0.244837` 改成 `0.001224`，变成 **1/200**，相当于在两个方向显著增加点状填充展开量。这也改变了图面，不只是慢。

- [上游 #1391：Hatch pattern scale issue](https://github.com/mozman/ezdxf/issues/1391)，修复提交 [de85835](https://github.com/mozman/ezdxf/commit/de8583515fdb48c3505a46f3e3d64187a79ede6d)：按变换的相对比例处理已实现的 pattern。
- [上游 #1399：重复旋转](https://github.com/mozman/ezdxf/issues/1399)，修复提交 [b3eb37b](https://github.com/mozman/ezdxf/commit/b3eb37b942acb4c7e2d2487706e614aa29b7f9b2)：纯平移不再把已有角度再次旋转。
- [上游 #1402：原点未平移](https://github.com/mozman/ezdxf/issues/1402)，修复提交 [163832f](https://github.com/mozman/ezdxf/commit/163832f3be73ed0fe600ec01b96b9999fa6549a1)：pattern base points 随边界作完整仿射变换。
- [正式版 1.4.5](https://github.com/mozman/ezdxf/releases/tag/v1.4.5)与[该版本源码](https://github.com/mozman/ezdxf/blob/v1.4.5/src/ezdxf/entities/polygon.py)包含三项修复。没有直接打补丁改第三方库，也没有引用不固定的 master 作为运行依赖。

回归脚本 `scripts/cadcraft/test-hatch-transforms.py` 在 1.4.4 下失败，在 1.4.5 下通过。覆盖小比例、原始角度、旋转 / 均匀缩放、两层嵌套 INSERT，通过实际虚拟实体展开与独立矩阵结果比对。未声称覆盖非均匀缩放、任意倾斜 OCS 的全部情况。只读递归检查本次保留源DXF的Model和两个paper blocks，可达patterned HATCH共210次（Model200、paper10）；累计INSERT的XY变换未发现非均匀、剪切或负行列式镜像链。关键“地面图例”块为纯平移，内含AR-CONC .008、AR-SAND .005、DOLMIT .05；另有拆除图例ANSI38原角度45。对象元数据检查有助缩小风险，但不代替图面核验。

首轮记录把 `page-026` 错称为天花图，已按来源清单更正：实际是 **P-06 地面铺贴图**，天花布置图是 page-027。

整份任务 `f356c9c7-302f-4589-9048-ddcc9de40137` 在Model总览完成原色PDF/PNG后，于阅读版PDF阶段触发单页120秒限制；只完成部分总览配色，不提供整套文件，源SHA-256不变。因此，升级解决了指定平面布局的主要瓶颈，**尚未解决带全局总览的整份快速导出**。

## SVG 后端整份实验：生成通过，图面一致性筛查未通过

在正式版ezdxf1.4.5上复用同一份保留XCLIP的原DXF、所有71页相同窗口、原色及阅读配色，隔离的SVG→MuPDF实验完成 **68张图框+3张总览**：渲染进程总计 **137.65秒**，采样物理峰值约 **1344.5MiB**。计时从启动缓存DXF渲染子进程开始，不含上传、DWG解码、图框识别或PDF合并，不能称为网页端到端2分17秒。没有因为标准整份任务失败而给它改成功状态，这是独立的实验输出。

每页SVG先把ezdxf的CSS class展开为presentation attributes，再交给MuPDF；任何实际IMAGE绘制记录直接拒绝、任何MuPDF警告直接失败，不允许静默丢图。源图本身缺失的外部图片仍需警告。实验产物、合并PDF、来源清单与对照HTML都在 `.local/cad-export-api-qa/followup/svg-all-pages/`。此后端暂未接入网页/API默认流程。

该实验通过“所有识别页生成”这一关，但**没有通过与标准后端的图面一致性筛查**：page-026地面图例中的“走边波打线”实心块显示不同。13张平面页归一化比较的平均通道绝对误差最高7.49/255，亮度差超过32的像素占比最高6.181%；线条对齐与抗锯齿也会计入该差异，不能把它直接当漏图率。可见的图例差异需要单独解释，不能因为总览整体相近就放行。

当前没有源CAD正式打印基准，不能仅凭两后端不一致判定哪条更接近源图。但足以拒绝在要求一致性的默认流程中静默切换。实验清单增加 `validation.status=failed-visual-consistency`，对照HTML明确标记未验收。SVG丢失PDF OCG图层、纸张取整不同，IMAGE仍不支持。当前建议：网页指定平面布局采用已验证的标准后端；SVG作为全稿提速候选继续核验，不为了提速静默改变默认渲染语义。

## 已落地与未采用的路线

已将 `render-requirements.txt` 锁定到 ezdxf1.4.5；启动器和裁剪导出预检拒绝旧版本，Python渲染入口也有版本检查，清单记录ezdxf/PyMuPDF版本。保留原PDF后端和完整填充，未通过隐藏填充、改成实心填充、降低分辨率来取得上述结果。

SVG路线没有接入正式导出。在修正上游填充变换后，隔离的SVG→MuPDF实验已将同一Model总览两种配色PDF/PNG于35.60秒生成（进程总计36.16秒），采样物理峰值1367.6MiB。对原PDF后端输出的原色总览按3000×2121归一后，平均通道绝对像素误差约0.27/255，亮度差超过32的像素占0.322%；此指标只作筛查，并非99.678%准确率或源CAD等价证明。源PDF与SVG的纸张矩形分别1190×841pt与1190.551×841.890pt，存在取整差。除前端瓶颈外，合成实验还证实直接交给MuPDF会忽略ezdxf使用的CSS class，必须先展开为presentation attributes；SVGBackend自身未实现IMAGE，必须拒绝或回退；两种后端纸张取整也不同。[PyMuPDF官方](https://pymupdf.readthedocs.io/en/latest/document.html#Document.convert_to_pdf)对SVG转换效果本身也只给有限评价。修复上游变换更直接，不需要引入这条新风险路径。

原生引擎与授权可行性另见[补充研究](2026-10-21-cad-native-export-followup.md)。ODA / AutoCAD / APS仍是对照候选，尚未以本图实测，不在本次“已通过”名单中。
