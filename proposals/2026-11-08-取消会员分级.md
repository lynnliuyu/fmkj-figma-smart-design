## 0. 变更摘要（§0.1 规定格式）

```
修改前：
  账号按会员等级（Go=free / Plus=pro / Pro=team）分级。
  Users 有 membershipTier（select）与 membershipExpiresAt（date）两个字段；
  细分级通过 src/lib/membership.ts 承载（MEMBERSHIP_TIERS / MembershipTier / resolveMembership /
  tierMeta / meetsTier / tierBadge / featureAccess 等），由 src/lib/membership-policy.ts 读取
  「会员设置」global 决定「提示模式 / 严格模式」。
  等级实际决定：可用项目数上限、每项目协作成员上限、每月赠分、可用的方案模板、可用的插件、
  可用的 AI 模型、交付资料包能否打包；并渲染到会员页、插件市场、方案模板、文档中心、小程序等处。
  兑换码可开通/顺延等级时长。AI 模型与插件各自带 tier 门槛。

修改后：
  取消会员分级，不再有 Go / Plus / Pro / Team 档位，不再按等级限制任何功能。
  所有功能统一按积分扣除（积分余额 = users.aiCredits，流水 = ai-credit-ledger）。
  清空 users.membershipTier / users.membershipExpiresAt 的值（字段是否整体删除见「未决问题 Q1」）。
  「会员设置」global 的 enforcement（提示/严格模式）失去意义；
  upgradeHint 是否保留、会员页如何改名，见「未决问题 Q2/Q3」。
  保留 aiCredits 与 AiCreditLedger 全套逻辑（发放/扣减/钩子/权限）。
  当前无实际购买订阅的客户 → 不做折算、不做补偿。
  现阶段只做个人账号；公司账号以后再说（不在本提案范围）。

影响范围：
  数据模型：users（2 字段）、redemption-codes（grantTier/durationDays）、
    proposal-templates.tier、ai-settings.aiModels[].minTier、plugins 清单的 tier 字段；
    生成类型 src/payload-types.ts 需重新生成。
  服务端逻辑：插件门槛、模板门槛、AI 模型门槛、项目数上限、协作成员上限、每月赠分、
    兑换码核销、使用报告/诊断。
  前端页面：会员与积分页、会员弹窗、插件市场、方案模板库与模板详情、打印页锁、归档交付包、
    文档中心、设置-运营报告、工作台侧边栏；小程序「我的」「方案」「AI」页。
  入口/导航：侧边栏会员徽章与会员弹窗。
  离线/导出物：docs/USER_MANUAL.md、knowledge/*.json（脚本导出）、promotion-kit 推广文案。
  迁移：新增一条 Payload migration（命名沿用现有约定）。

数据迁移 / 兼容：
  users.membershipTier 现为 required select（default 'free'）、membershipExpiresAt 为可空 date。
    「清空」= 把两个字段值置空/置默认（见 Q1）。
    DB 层若选择删列，先例见 migration 20261031_161835_membership_codes.ts 的 down（已 DROP
    users.membership_tier / membership_expires_at / _users_v 对应列 / 相关 enum 类型）。
  兑换码：现有 grantTier（none/pro/team）、durationDays 字段与新语义（仅积分）不符，需处理（Q4）。
  模板 tier、AI minTier、插件 tier：这些是「门槛」而非业务数据，
    移除后不需要数据回填；但 admin 后台已有的人工配置（若曾把某模型设为 pro/team）会作废。
  无付费客户 → 无退款/折算/补偿；不做用户数据导出。
  回滚：本变更可逆（见「回滚方式」）；但一旦有用户在新模型下消耗积分，回滚不会恢复等级门槛配置。

回滚方式：
  代码：revert 本变更涉及的分支/提交（保留原 membershipTier 列即最易回滚）。
  数据：若采用「删列」方案，回滚需再写一条 migration 重建列与 enum，
       并按「清空前的值」恢复（若无备份则等级值无法还原 → 采用删列前须先备份，见 Q1）。
       若采用「保留列 + 置空值」方案，回滚只需把代码切回旧逻辑，等级值依赖置空前的备份。
  结论：推荐先备份 users 的 membershipTier/membershipExpiresAt 快照，再执行变更。

需要谁批准：
  项目 owner（noone）。属 §0.1「数据模型、字段语义、权限模型、导航层级」变更，必须书面批准。
  批准后按 §0.1 更新 PROJECT-ARCHITECTURE.md 并改代码。
```

### 1.3 `aiCredits` 与 `AiCreditLedger` 现状

- 集合：`src/collections/AiCreditLedger.ts`（slug `ai-credit-ledger`）。
  - 权限：`read: ownOnly`、`create: cmsAdminOnly`、`update/delete: ()=>false`（`AiCreditLedger.ts:22-27`）。
  - `beforeChange`（`:30-45`）：仅 `create` 时计算 `balanceAfter = user.aiCredits + delta`，`balanceAfter<0` 抛 402。
  - `afterChange`（`:46-58`）：把 `balanceAfter` 写回 `users.aiCredits`。
- `users.aiCredits`（`Users.ts:88-96`）为 `readOnly`，任何人不能直接改，只能经流水。
- 与 membership 的**耦合点仅两处**：
  1. 兑换码 `redeemCodeForUser` 同时写流水 + 改等级（`membership-service.ts:120-133`）。
  2. 每月赠分 `claimMonthlyCredits` 的数量来自档位 `monthlyCredits`（`membership/actions.ts:22`）。
- 除此之外，额度与流水**不依赖** membership：积分任务奖励 `src/lib/credit-tasks.ts`、AI 对话扣费（`ai-credit-ledger` 负数流水）均独立。
- 结论：清空等级不影响积分余额与流水，只需拆掉上述两处耦合（兑换码改为纯积分；每月赠分见 Q5）。

## 3. 风险与未决问题

### 3.1 风险

1. **引用面极广**：`membership.ts` 的导出被 ~15 个模块、数十处页面引用（1.2 全表）。改造是「删除式」，漏改一处会导致编译失败或运行时行为不一致。
2. **权限放宽**：取消门槛后，原 Plus/Pro 独占的插件、模板、满血推理模型将对所有账号开放。若有人借此高频调用高价模型，成本风险上升——因此**积分计费（`cost` 倍率）必须可靠**，这是放开门槛的前提。
3. **积分余额与等级解耦的两处耦合**（兑换码、每月赠分）若处理不当，可能误扣/误发积分。
4. **迁移不可逆性**：若采用「删列」方案且未备份等级快照，回滚无法恢复用户原等级。
5. **离线产物时间差**：`knowledge/*.json`、`docs/USER_MANUAL.md`、`promotion-kit` 若不同步，对外口径会残留 Go/Plus/Pro。
6. **小程序/多端同源**：网页、小程序、mp API 共用同一批库与类型，改造需三端一起验证。
