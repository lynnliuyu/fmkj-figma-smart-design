**真机上暴露并修掉的问题**（本地测试测不出来，都是实跑才出现的）：
装机 uid 1001 写不进 root 目录（EACCES）；compose 会「继承」机器上已有容器的项目名，导致测试实例
误动正式容器；`.env` 重复键让更新静默退回旧版本；升级时提交请求的是旧版本应用（要兼容老路径）；
自签仓库的 CA 要给 Node；报价页被预渲染缓存导致品牌不生效；更新只换镜像不同步宿主机脚本。
每条都在提交信息与本文对应小节里写明。

**还没做**（别当成已满足）：
真机上的**失败路径复测**（断电、拉取失败、迁移后失败）只有单测覆盖，没在设备上真复现过；
**真实打印**（打印机 / 导出 PDF 的边距分页）没验过，只在屏幕上渲染确认；
托管版运维、多实例、换机搬迁、AI 自动布点与自动报价仍为规划；
报价单上的客户联系人/电话尚未支持（只有客户项目名）。

## 目标

1. 本地设备能用一条命令把软件更新到**明确版本**，并且失败时不会把设备留在半新半旧的状态。
2. 更新前一定有可恢复的备份；迁移后的失败不假装能靠切镜像回滚。
3. 划清「哪些功能接口对接运营方服务」的边界与合同，为收费订阅留出实现位置。

## 非目标

- 不做自动跨版本升级；定时任务只提示，不代管理员决定版本。
- 不做产品库同步的具体实现（数据模型属 Plan 028）。
- 不把客户项目、点位、报价、交付、上传附件纳入任何上游请求（ADR 0010）。
- 业务容器不获得 docker socket 或宿主机命令执行能力（ADR 0010）。

使用独立的临时数据库 `fmkj_rehearsal`，未触碰开发库 `fmkj`：

| 场景 | 结果 |
| --- | --- |
| 首次部署 `--to v0.1.0`（真实 `next build` 镜像 → 推送 registry → 拉取 → 迁移 → 切换 → 校验） | 六步全过 |
| 更新 `--to v0.2.0` | 通过；`/login` 200、容器 `FMKJ_VERSION=v0.2.0` |
| 独立核对（不看脚本自报） | 演练库 37 张表，关键表齐全；`schema_migrations` 26 条 |
| 备份可恢复性 | `pg_restore --list` 读出 74 个对象；**真实恢复到临时库得到 37 张表和 26 条迁移账本** |
| 失败 A：目标镜像不存在（拉取失败） | `abort`，旧容器继续服务（`/login` 200、版本仍 v0.2.0），进程退出码 1 |
| 失败 B：迁移已执行后 verify 失败 | `failed-needs-restore`，**容器仍停在 v0.3.0，没有自动切回旧镜像**，状态里记录备份位置 |

演练中修掉的真实缺陷（都是只有真跑才会暴露的）：

1. `backupDir` 用正则从中文提示里抠路径，被全角括号污染成 `…-before-v0.1.0（0.0`，
   失败提示里的备份路径不可用 → 备份脚本改为输出机器可读的 `backup_dir=`，并加回归测试。
2. `backup` 排在 `fetch` 之前，导致**每次版本号打错都留下一个完整备份**（演练里 4 次尝试
   产生 4 份）→ 调整为 `preflight → fetch → backup → migrate → switch → verify`，仍保证
   「迁移前一定有备份」。
3. 探活失败只报 `fetch failed`，看不到真因 → 现在带上 `cause.code`（如 `ECONNREFUSED`）。
4. 备份脚本写死卷名 `fmkj-v3-uploads`，而 compose 的卷是可参数化的 → 改为读
   `FMKJ_UPLOADS_VOLUME`，否则会备到别的卷上还以为成功。
   同批修正：文档里的恢复命令原本写成 `-e PGURL="$DATABASE_URL"`，会把密码带进宿主机
   `ps` 参数；改成裸 `-e PGURL`。

仍未做的验收（真机部分已于 2026-10-21 完成，见 033.5）：「两人同时更新」的维护锁只做了代码路径检查，未做并发实测。

### 033.5 黑豹 X2 真机验收（2026-10-21 完成）

实机：黑豹 X2（RK3566 / arm64 / 3.8 GiB 内存 / 29G eMMC 用 13%）+ Armbian 26.11（Debian 13）
+ Docker 26.1.5 / Compose 2.26.1；设备上另有在跑的 goofish 服务栈，全程未受影响。

| 场景 | 结果 |
| --- | --- |
| 本机交叉构建 arm64 镜像 | `fmkj-v3:v0.1.0`、`v0.1.1` 均为 linux/arm64 |
| 首次部署（设备版编排：应用 + 设备本机 Postgres） | 起库 → 迁移 24 项 → 建管理员 → 起应用；`/login` 200、容器 `FMKJ_VERSION=v0.1.0` |
| 设备数据库 | `fmkj-v3-db` 容器 + `fmkj-v3-db` 卷，37 张表 |
| 备份（真机） | `docker compose exec` 路径产出 108K custom dump（239 个 TOC 条目）+ 上传卷 + metadata |
| 备份可恢复性 | **真恢复**到临时库：37 张表 + 26 条迁移账本，随后清理 |
| 更新 `v0.1.0 → v0.1.1` | `--source registry` 从自建 TLS 仓库拉取，六步全过，1m39s；`/login` 200、容器 `FMKJ_VERSION=v0.1.1`、`.env` 写回新版本 |
| 登录会话（真机 http 访问） | `Set-Cookie` 不再带 `Secure`；带 Cookie 访问 `/api/projects` 返回 200 |
| 真实浏览器渲染 `/login` | 34 KB DOM，登录 / 邮箱 / 密码字段齐全 |

真机发现并修掉的问题（都只有在真实 Linux 设备上才会暴露）：

1. **宿主机访问数据库在 Linux 上不通**：`docker run postgres:17-alpine psql/pg_dump` 在默认 bridge
   上既解析不到宿主机也解析不到 compose 服务名；macOS 的 Docker Desktop 会注入
   `host.docker.internal`，所以演练能过、真机会挂。→ 更新校验与备份改为 `docker compose exec`
   进数据库容器（本地 socket，不需要连接串，也不依赖宿主机网络）。
2. **会话 Cookie 强制 `Secure`**：取 `NODE_ENV === "production"` 会让 `http://<设备IP>:3000` 下
   浏览器不保存会话 Cookie，表现为「登录接口 200，人却还是未登录」。→ 按 `x-forwarded-proto`
   判断，并提供 `AUTH_COOKIE_SECURE` 显式覆盖。
3. **宿主机没有 Node**：更新 / 备份是宿主机侧 Node 脚本（ADR 0010 要求业务容器不持有 socket），
   Armbian 不自带 Node。→ 随设备放一份 Node 22 运行时（`/opt/fmkj/tools/node`），文档补上前置条件。
4. **更新成功后没写回版本**：`.env` 里仍是旧镜像，下次有人直接 `docker compose up -d` 会静默退回
   旧版本。→ `switch` 成功后把 `FMKJ_IMAGE` / `FMKJ_VERSION` 写回 compose 插值文件。
5. 备份 `metadata.json` 记的镜像取的是 compose 兜底值（`fmkj-v3:latest`）而不是实际版本。→ 改为优先
   读环境变量与 `.env`。
6. 设备**拉不通 Docker Hub**，而设备上需要业务镜像 + `postgres:17-alpine` + `alpine` 三个镜像。→
   设备版编排允许 `POSTGRES_IMAGE` 指向自建仓库副本；文档写明三个镜像的来源与离线导入方式。

仍未做的验收：

- 033.2 的现场照片越权 404、本地存储商品图冻结进固定交付版本。
- 033.4 管理端只读展示更新状态。
- 真机上的**失败路径**复测（`abort` / `restart-previous` / `stop-for-restore`）只在 macOS 演练过。

### 033.6 数据来源两档（2026-10-21 真机验证）

用户确认的形态：**一套业务核心，数据来源可选**——默认设备自带库，也可以接用户自己的 PostgreSQL。

| 档 | 编排 | 真机结果 |
| --- | --- | --- |
| 默认：设备自带库 | `docker-compose.appliance.yml` | 首次部署、更新、备份、真实恢复全部通过 |

`docs/local-appliance-deployment.md` 第 1.1 节。

业务数据按 ADR 0010 不经过任何上游接口。

### 033.9 官方产品资料同步（2026-10-22 实现第一版，快照式）

用户选择「传表格文件导入」与「从我的服务器同步」两条都要。第二条的第一版按**快照**实现，
不按合同的增量游标实现；差距与原因写在 `docs/local-appliance-deployment.md` 第 5 节。

| 交付物 | 说明 |
| --- | --- |
| `lib/catalog-sync.ts` | 配置解析（`UPSTREAM_*`）、快照拉取（Bearer + 实例标识 + 摘要校验）、发布端 CSV 导出 |
| `lib/catalog-sync-service.ts` | 预演与应用、`catalog_sync_runs` 运行记录、未配置时的可照做提示 |
| `GET /api/catalog/snapshot` | 运营方侧发布（`CATALOG_PUBLISH_TOKEN` 定时比较 + 401；未配置时 404 关闭）；只发布已通过审核的产品 |
| `POST/GET /api/admin/catalog/sync` | 管理员侧状态、预演、应用 |
| 产品管理 →「从服务器同步」 | 显示配置与上次结果；预演差异（复用批量导入的差异表）；**默认只补新品**，勾选后才覆盖已有产品 |
| `scripts/create-catalog-sync-runs.sql` | 同步批次表（资料版本、计数、失败原因、操作人） |
| `tests/catalog-sync.test.ts` | 16 项：配置与提示、凭据与摘要校验、离线原因、发布/回灌同一份内容互不改变、策略传递、运行记录（含失败） |

三条关键语义（测试钉住）：

- **默认不覆盖已有产品**。官方资料里的价格未必等于本地调过的价格，静默覆盖是数据事故；
  要覆盖必须管理员显式勾选，且预演会如实显示「哪些会被覆盖」。
- **失败不动本地**。连不上、凭据失效、摘要不符都只记一条失败记录，本地资料与业务继续可用。
- **摘要不是签名**。`X-Catalog-Sha256` 只能发现截断或改动，不能证明发布者身份；验签未实现。

真库端到端（2026-10-22，临时库 `fmkj_sync_e2e`，跑完即删，未触碰开发库）：
用真实发布端代码导出快照 → 真实 HTTP 服务提供 → 设备侧预演/应用 → psql 独立核对。
覆盖：预演不写库、三个产品写入且价格成本一致、本地改过的价格在默认策略下保持 999 不被覆盖、
显式勾选后恢复为官方 199、每次应用留一条运行记录、服务不可达时记录 failed 且本地一字未改。

新迁移 `create-catalog-sync-runs.sql` 已在临时库的完整迁移链上验证通过（26 项）。

定时同步（2026-10-22 补做并真实验证）：应用进程内排期（`instrumentation.ts` + `lib/catalog-sync-schedule.ts`），
默认启动 5 分钟后首次、之后每 24 小时一次，可用 `UPSTREAM_SYNC_ENABLED=false` 关掉。
真实验证：临时库 + 本地资料服务，应用启动后**无人干预**第 1 秒就完成同步（日志「新增 2、更新 0、跳过 0、失败 0」），
psql 独立核对产品、批次记录与审计（无操作人时 actor 为空，不编造用户）。
过程中修掉一个真缺陷：定时同步没有操作人，原先把空字符串当 userId 传给 `$1::uuid`，每一行都写失败（日志只显示「失败 2」）。
现在 `actorUserId` 允许为 null，并加了回归测试钉住。

未做：验签、增量游标与分批、本地覆盖的逐项冲突处理、素材下载、订阅到期与宽限期。

- **以系统货号认人**。库里没有就新增（状态 `pending_review`，等后台审核）；已有就只覆盖写了的列；完全一致就跳过，不写库也不记审计。同一文件里同一货号出现两次判为错误。

- 真实运行中的服务工作台（789 个真实产品）上验证模板下载与预演：模板 200 且带 BOM；未登录 401；预演正确分出「不变 / 覆盖（逐字段列出改名改价）/ 新增 / 行内错误」，预演不写库。

### 033.10 客户自助备份导出与恢复（2026-10-22 已实现并连真库 + 真 HTTP 验证）

用户 2026-10-21 确认：不要定时备份与换机搬迁，改为**备份导出 + 备份还原，客户自己在网页上操作、自己保存文件**。

| 交付物 | 说明 |
| --- | --- |
| `lib/backup-archive.ts` | 极小的 tar 读写（ustar + GNU 长名 + PAX 兼容）；只依赖 Node 自带 zlib，不引二进制依赖 |
| `lib/backup-service.ts` | 导出：整库逐表 `COPY ... TO STDOUT (FORMAT csv, HEADER)` + 附件打包 + manifest（含结构指纹与每表摘要）；恢复：校验后在一个事务里 `truncate ... cascade` + `COPY FROM STDIN`，`set local session_replication_role = replica` 处理自引用外键 |
| `GET/POST /api/admin/backup` | 导出流式下载；恢复用原始请求体上传（不是表单，省一次内存复制） |
| 系统健康 →「备份与恢复」 | 导出按钮 + 恢复（必须手工输入「恢复」两个字才可点） |
| `pg-copy-streams` + `@types/pg-copy-streams` | 新增依赖：`COPY FROM STDIN` 的协议实现，自己写不现实；零依赖、node-postgres 官方组织维护 |
| `tests/backup-archive.test.ts` | 6 项：与**系统自带 tar** 的真互操作（ustar 前缀、GNU 长名）、多字节内容、路径安全 |

关键语义：

- **恢复是整体替换，不是合并**；任何校验不过就整体回滚，本地数据一点不动。
- **结构指纹**（`information_schema` 的表/列形状摘要）对不上就拒绝：备份来自另一版软件时先升级。
- 每张表的 CSV 带 sha256，传输损坏或被人改过都能发现。
- 附件只增不删；`schema_migrations` 不进备份（它描述的是当前结构，恢复它反而会改错记录）。
- **应用起不来时网页也打不开**，所以宿主机 `pg_restore` 那条路（文档第 4 节）仍是兜底，文档里写明了。

真库端到端（临时库 `fmkj_backup_e2e`，跑完即删）：导出清单正确、`schema_migrations` 不在内、
系统 tar 能列出并解出可读 CSV；结构指纹被改 → 拒绝且数据不动；CSV 被追加内容 → 拒绝且整体回滚；
完整旅程「导出 → `truncate products` → 还原」后产品、附件、结构指纹与原状一字不差。

真 HTTP 端到端（构建产物 + 真实会话，指向临时库）：42MB（含一个 40MB 不可压缩附件）的备份
0.7 秒流式下载完、gzip 与 tar 校验通过、未登录 401。

**过程中发现并修掉的真问题**：中间件会按 `proxyClientMaxBodySize`（32MB）复制请求体，
42MB 的备份传回去被截断成坏包。修法是让 `/api/admin/backup` **不进中间件**——该路由自己调
`requireSuperAdmin()` 且先校验后读体，未登录请求 0.14 秒被拒、不会把 42MB 读进内存。
修复后同一份 42MB 备份恢复成功（29 张表、附件 2 个），psql 独立核对数据与附件都在。

未做：跨版本/跨结构的备份迁移（只支持同结构）、备份加密与密码保护、恢复进度条（大包上传时只有一个转圈）。

### 033.12 在线更新：客户在页面上点按钮（2026-10-22，真机联调）

用户要求：「客户都是不懂代码的，在平台加个检查更新、在线更新的按键」。已实现并在真机
（10.0.0.134，Armbian 26.11 / aarch64，与出货同型号）跑通。

链路（不破 ADR 0010）：

    页面写请求（只有版本号）→ deploy-state/requests/update-request.json
    → 设备上的更新管家（systemd，5 秒轮询）校验后调用既有更新脚本
    → 进度与结果写回 updater-state.json → 页面显示

**真机上跑出来的结果**：

| 步骤 | 结果 |
| --- | --- |
| 首次更新（保底命令）v0.1.4 → v0.3.0 | 六阶段全绿：preflight / fetch / backup / migrate / switch / verify |
| 页面「检查有没有新版本」 | 通过，5 秒内回结果 |
| 页面「立即更新到 vX」 | v0.3.0 → v0.3.1 → v0.3.2 两次都成功；页面显示「已完成更新到 vX」，容器镜像与 .env 同步 |
| 出货权限配置下复测 | deploy-state 归 root、只有 requests/ 归应用用户（1001）：点检查仍 200，应用日志无 EACCES |

**只有真跑才会暴露、已修掉的问题**：

1. **应用写不进 deploy-state**（EACCES）：容器以 1001 运行，而该目录由 root 创建——和当年首次
   上传 EACCES 同类。改为请求单独放 `requests/` 子目录（归 1001），管家状态与日志留在上一层
   （root 拥有，应用读得到、改不了）；编排加 `deploy-state-init` 一次性修权限。
2. **升级时提交请求的是「还没升级的那个版本」**：老版本应用写在 deploy-state 根目录。管家现在
   两个位置都认（先新后旧），否则第一次点按钮的老设备永远升不上来。
3. **页面「当前版本」会过期**：它读的是上次检查的快照，更新完就会显示旧版本，还会允许「更新到
   已经在跑的版本」。改用容器自己的 `FMKJ_VERSION`，并拒绝空转更新。
4. **自签仓库 Node 不认**：Docker 通过 `/etc/docker/certs.d/<仓库>/ca.crt` 信任，Node 不读那里。
   设备上把 CA 指给 Node（`NODE_EXTRA_CA_CERTS` 写进 `.env`），两个 systemd unit 都用
   `EnvironmentFile=-/opt/fmkj/app/.env`，换证书不用改 unit。

**首次安装仍需一次命令**：老版本应用里没有按钮，所以第一台（次）升级只能用第 3 节的命令；
装上带按钮的版本并部署更新管家之后，后续都点按钮。

**未做**：真机上的失败路径复测（断电 / 拉取失败 / 迁移后失败）——处置逻辑有单测覆盖，但没在
设备上真复现过；订阅授权与到期、托管版多实例仍为规划。

## 已确认的边界

- 备份 = 数据库 + 上传卷 + 配置；只 dump 数据库不算备份（ADR 0010）。
- 不为部署新开公开接口；校验用 `/login` + 容器环境 + 直连数据库。
- 更新必须针对明确版本；`latest` 被脚本拒绝。
- 迁移前的备份是硬前提，`--skip-backup` 只为「已确认有备份」的场景保留，且在状态里如实记录。
