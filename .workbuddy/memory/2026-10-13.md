## 排查「显示账号密码错误」（继续）

用户反馈登录时提示账号密码错误。核查结论：**服务端与数据库均正常**，问题在浏览器端填写的凭据。

已验证通过：
- 数据库里只有 1 个用户 `admin@fmkj.com`，bcrypt 哈希与 `Admin@123456` 比对返回 true。
- 实时接口 `POST /api/auth/login`（mode=password）→ 200 登录成功；故意用错误邮箱 → 401「邮箱或密码错误」。
- 验证码登录路径也通：`POST /api/auth/send-code` 在 `AUTH_DEV_MODE=true` 下直接把验证码放在响应里，
  再用它调 mode=code 登录 → 200。可作为免密登录的备用入口（前端「短信」标签页）。
- 本机只有 3000 一个本项目 dev server，不存在连错端口的情况。

推断：浏览器对 localhost:3000 存了旧的自动填充密码（本机多个项目都用过该端口），
点登录时自动填入了错误凭据。已建议清空输入框手动输入，或改用验证码登录。

### 最终定位与解决
用户确认用的就是 `admin@fmkj.com / Admin@123456`，于是逐字符比对密码变体，实测：

| 输入 | 结果 |
| --- | --- |
| `Admin@123456` | 200 |
| `Admin@123456 `（末尾多空格） | 401 |
| ` Admin@123456`（开头多空格） | 401 |
| `admin@123456`（大小写不同） | 401 |

**根因：登录接口 `loginWithPassword` 只对邮箱做 `trim().toLowerCase()`，密码是原样 `bcrypt.compare`，
首尾多一个空格即失败。** 从聊天窗口复制密码极易带上尾随空格。

处理：用 `pnpm db:seed-admin --password=admin123456` 重设为纯小写加数字的简单密码（不易被误输入），
curl 与真实浏览器均验证登录成功，旧密码已失效。

**未改动的点**：密码不做 trim 是有意保留的（与邮箱的处理不一致，但改动属于认证语义变更，
需用户确认）。如果后续要防呆，可在 `app/api/auth/login/route.ts` 里对密码也做 trim。

## 环境问题：系统代理导致内网地址打不开（2026-10-14）

用户反映 `http://10.0.0.1/`（路由器管理页）打不开。**根因是系统代理，不是路由器故障。**

### 诊断证据
| 测试 | 结果 |
|---|---|
| ping 10.0.0.1 | 通，0% 丢包，RTT 约 5ms |
| 80/443 端口 | 均 OPEN |
| 直连 HTTP（`--noproxy '*'`） | **200，0.011s** |
| 经系统代理 127.0.0.1:1075 | **000 超时 8s** ← 根因 |
| 1075 端口进程 | `sing-box`（PID 16099） |
| 经 1075 访问 google.com | 302（代理本身正常） |

路由器固件是 **Kwrt / LuCI**（OpenWrt 分支），nginx 1.26.1，首页 meta refresh 跳 `/cgi-bin/luci/`。

### 根因
`scutil --proxy` 显示 HTTPEnable/HTTPSEnable/SOCKSEnable 全为 1，代理 `127.0.0.1:1075`（sing-box），但**例外列表只有 5 个百度域名，没有任何内网段**。浏览器遵循系统代理，把 `10.0.0.1` 的请求也交给 sing-box 转发到远端 → 超时 → 页面打不开。

curl 之所以一直能通，是因为它读的是环境变量 `HTTP_PROXY=127.0.0.1:53661`（WorkBuddy 沙箱代理，配了内网直连），**不是系统代理**——排查时容易误判。

### 已做的修复
```bash
networksetup -setproxybypassdomains "Wi-Fi" \
  "10.0.0.0/8" "192.168.0.0/16" "172.16.0.0/12" "127.0.0.1" "localhost" "*.local" \
  "*.baidu.com" "*.shifen.com" "*.bdstatic.com" "*.bdimg.com" "*.baidubce.com"
```
（保留了原有百度域名；原列表备份在 `/tmp/proxy_bypass_backup.txt`）

⚠️ **这个修改不持久**：sing-box 这类客户端在启动/重连/规则更新时会重写系统代理设置，可能清掉 bypass。**更彻底的做法是在 sing-box 配置里加直连规则**（route.rules 中 `ip_is_private → direct`，或把 10.0.0.0/8 加入直连列表）。

`10.0.0.176`（旧数据库主机）**直连仍然超时**（000，3s）——这台机器确实是宕机状态，与代理无关，进一步印证了之前「旧数据在远程库且主机不可达」的结论。`10.0.0.104` 主机在线但 80 端口无服务。

## 改 PVE 网络配置的安全做法（通用技巧，2026-10-14）

改 PVE/远程 Linux 主机的网络配置有**失联风险**（配置写错就彻底连不上，只能到物理控制台救）。安全的做法是**改前备份 + 设置自动回滚倒计时**：

```bash
cp /etc/network/interfaces /etc/network/interfaces.bak
nano /etc/network/interfaces            # 改 address / gateway
(sleep 300 && cp /etc/network/interfaces.bak /etc/network/interfaces && ifreload -a) &
echo $! > /tmp/rollback.pid
ifreload -a                              # 应用
# 立刻用新 IP 测试：成功则 kill $(cat /tmp/rollback.pid)；失败则什么都不做，5 分钟后自动还原
```

要点：
- `address` 与 `gateway` 必须**同时改**，只改 IP 不改网关等于没网
- 改前用 `ip a` 确认 `vmbr0` 绑定的物理网卡名
- 新 IP 要选在 DHCP 池外（如 10.0.0.200），避免冲突
- PVE Web UI 路径：节点 → System → Network → 编辑 vmbr0 → Apply Configuration（应用后连接会立即断开，属正常）
- 只动 address/gateway，不要碰 vmbr0 的 bridge-ports（否则虚拟机会断网）

## 图片存储约定（2026-10-15 12:20 确认）

产品图片有两条通路，**实际统一走本地**：

| 通路 | 说明 | 实际使用 |
|---|---|---|
| **本地 public/** | 图片放 `public/assets/products/...`，DB 存 `/assets/...` 相对路径 | **745 / 747 条** |
| Vercel Blob | `POST /api/upload`（`kind=product_image`）上传到 `@vercel/blob` 的 `product-images/` 目录，返回远程 URL | **0 条** |

- `BLOB_READ_WRITE_TOKEN` 在 `.env.local` 中**已配置**，所以 `/api/upload` 本地可用，但没人用它传产品图。
- **采集入库时继续沿用本地 `public/assets/` + `/assets/...` 路径**，与既有 745 条保持一致；不要改成 Blob URL，否则本地开发会变成拉远程图。
- 改图两条路径都会 `freezeProductQuoteSnapshots`（`lib/product-admin-service.ts:160` 的 `updateAdminProduct` 与 `app/api/products/[id]/image/route.ts` 都调用），所以走通用 `PATCH /api/admin/products/{id}` 改图**不会漏冻结报价快照**。
- 注意：`GET /api/admin/products/{id}` 不存在（405），更新时要从列表接口取完整记录。
